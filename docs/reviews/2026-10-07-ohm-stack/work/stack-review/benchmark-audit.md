# Ohm benchmark and attribution audit

Audit date: October 5, 2026. The released reference is `ohm-1.99.0-1`; experiment PRs can be newer than that release. This report evaluates evidence for retaining changes, not their correctness or source complexity. See the component audits for exact inclusion and dependencies.

The existing measurements establish that the **bundle** is useful. They do not establish that every optimization in the bundle is useful. The largest independently measured benefit is public API hashing; many other patches have only sub-percent instruction savings, synthetic wins, benefits in a debug configuration that Ohm no longer uses by default, or inconclusive whole-session measurements. Those are appropriate deletion candidates when they carry significant integration or maintenance cost.

The arithmetic and original samples are retained in [published-benchmark-audit.json](evidence/published-benchmark-audit.json). It includes all 30 current workflow cells, all current/historical session totals, every slower session command, all nine published uv feature matrices, the disk comparisons, source SHA-256 values, and verbatim fetched PR evidence.

## What the released bundle demonstrably buys

[Current replay results](../../scripts/session_replays/release-1.99.0-1-baseline.json), two samples per toolchain/project:

| Session | Stock median | Ohm median | Less time | Absolute saving |
| --- | ---: | ---: | ---: | ---: |
| Ruff/ty component fixed points | 526.192 s | 362.370 s | 31.13% | 163.822 s |
| uv PyPI JSON parser | 169.857 s | 119.576 s | 29.60% | 50.280 s |
| Codex TUI active-cell layout | 632.049 s | 387.195 s | 38.74% | 244.854 s |
| Historical Ruff inherited attributes | 504.463 s | 353.004 s | 30.02% | 151.459 s |

The current three-session aggregate is 1,328.098 s versus 869.142 s, or 34.56% less time. This is an aggregate of three particular three-edit sessions; it is not a forecast for arbitrary developer histories or a decomposition into feature benefits. Baseline warmups are excluded; the fixtures are warm development workflows.

The [workflow report](../../scripts/benchmark_results/release-1.99.0-1.json) has 216 accepted samples. API-preserving dependency edits give conspicuous gains: uv check 12.970→1.093 s, Clippy 16.905→0.880 s, test 26.267→3.787 s; Codex check 21.603→1.627 s, Clippy 49.634→1.770 s, test 57.806→5.199 s. These support preserving the **early-cutoff/relinking family** as a core, while not independently defending every helper or cache in that family.

Build-to-check transition cells improve uv 70.464→23.896 s and Codex 125.536→63.674 s. Shared-worktree cells improve uv 9.544→1.639 s and Codex 3.975→0.754 s. Each is one sample per compiler: meaningful directional evidence, insufficient to price all cross-graph, worktree-seeding, trust, or locking machinery separately.

Warm Codex formatting improves no-op 11.911→0.308 s and direct edit 12.437→0.503 s. The benchmark explicitly runs an untimed formatting warmup and verifies a cache snapshot. This is strong evidence for the **base incremental formatting path** on a large warmed workspace. It is not independent support for each subsequent configuration, module-certification, or batching optimization.

The [APFS disk report](../../scripts/benchmark_results/disk-1.99.0-1.json) finds whole-bundle allocation reductions of 40.00/40.17/50.11% for Ruff with one/two/ten worktrees, and 35.11/46.97/58.27% for uv. It uses eight cohorts, 44 worktrees, 404 successful Cargo commands, and 53,664 test starts. Those savings are material. One cohort per arm, the same donor history across nine siblings, permissive macro/native-tool trust, and bundled debug/storage changes prevent attributing the savings to each separate compiler metadata format or seed feature. This is physical APFS allocation, not Linux/ext4 or logical target-directory size.

## The only published release feature matrix

The [uv matrix](../../scripts/session_replays/release-1.99.0-1-uv-feature-ablation.json) isolates two compiler options on the same released Ohm compiler. All other Ohm changes, debug defaults, trust and shared-build settings stay enabled. Each cell has only two measurements.

| API hashing | Proc-macro caching | Session seconds | Median |
| --- | --- | --- | ---: |
| On | On | 3.854456, 4.194974 | 4.024715 |
| Off | On | 6.932088, 7.070587 | 7.001337 |
| On | Off | 4.520578, 3.774144 | 4.147361 |
| Off | Off | 7.180006, 7.192923 | 7.186465 |

Public API hashing saves **3.007863 s, or 42.40%**, averaged across the other feature's settings. With proc-macro caching enabled, it saves 2.976622 s, or 42.52%. This is a clear large gain for this favorable private parser edit and its downstream check/test.

Proc-macro caching saves only **0.153887 s, or 2.72%**, averaged across API settings. With public API hashing on—the current default—the median difference is **0.122646 s, or 2.96%**. Same-repetition differences are +0.666122 s and −0.420830 s; the macro-disabled/API-enabled cell has a 0.746435 s range. The matrix therefore does not provide convincing precision for the small marginal gain. Its title describes derive-heavy tests, but changing a private parser file also permits module/query reuse; this does not test every derive workflow or macro cache's cross-worktree dimension.

The derive-cache implementation and flag are already upstream in Rust 1.99; Ohm adds enablement and related Cargo trust/reuse policy. Removing the upstream implementation would increase divergence. A weak result here therefore questions automatic enablement and additional trust/import machinery, not a nonexistent Ohm-only compiler cache implementation.

## Slower and weak parts of the released evidence

The headline tables appropriately preserve regressions. uv direct check is **3.474→3.714 s (+6.91%)** over five repetitions. uv cold check is **71.869→73.728 s (+2.59%)**, but has one sample. The complete current replay also has individual slower test, Clippy, and formatting commands even though session totals improve. These cannot be attributed to one patch from a whole-bundle comparison.

First whole-workspace formatting is slower in the real sessions: current Ruff **7.455→8.939 s (+19.9%)**, historical Ruff **7.464→9.843 s (+31.9%)**, and uv's first formatting command **3.811→4.655 s (+22.1%)**. Ruff's recorded warmups warm tests rather than formatting. Later uv formatting benefits can offset its first-format penalty; warm Codex microbenchmarks measure a different phase. Preserve the base warm formatting path provisionally, but require cold/first-format and mixed real edits when deciding whether later formatter layers pay for themselves.

No-op command improvements are often only tens or hundreds of milliseconds: uv check 22 ms, Codex check 107 ms, Clippy 144/102 ms, and tests 193/113 ms. They may matter at high frequency; they do not automatically justify elaborate extra schedulers, manifest/cache layers, or path validation. The report's 3/5/7 phase samples are better than one, but still describe one host and workload.

## Unshipped linker and optimized-release branches

The pinned [Wild whole-session report](evidence/wild-whole-sessions.md) is unusually informative because it tests the combined stack against the original linker, beyond isolated links. Six complete rounds each for uv and Ruff, three linker arms, counterbalanced orders, matched work, independent audits:

| Whole session | Upstream | Normal Wild stack | Change, paired 95% interval | ThinLTO/PGO stack | Change, interval |
| --- | ---: | ---: | --- | ---: | --- |
| uv |152.32s|149.64s|−1.76%[−6.72,+3.41]|153.59s|+0.83%[−0.47,+2.15]|
| Ruff |392.36s|395.37s|+0.77%[+0.10,+1.62]|395.15s|+0.71%[+0.27,+1.28]|

Codex is incomplete after a harness validation rejection: successful fixture commands do not make it a accepted completed result. No aggregate Codex estimate should be constructed from the partial run.

This is a strong reason to archive the broad `ohm-wild` optimization stack. The representative warm/tmpfs link endpoint improves 14–20%, but those gains do not translate to completed session savings in the measured ext4 workflow. Tmpfs page population is inactive on ext4 and is therefore not tested by the whole-session comparison; its isolated 6% link gain can remain a separate upstream proposal if worthwhile, without retaining the rest of the fork. The linker tests used a controlled SmallVec 1.15.2 override, not committed 1.16.0, and compare endpoint branches that include subsequent upstream differences: neither comparison prices every individual patch in isolation.

[Early fat-LTO function merging Rust#154](https://github.com/astral-sh/ohm-rust/pull/154) improves pinned Ruff entry edits 2.37% and target-cold 1.50%, but uv 0.45%/0.095% is inconclusive. This optimized release-build niche is small against keeping an extra compiler flag/pipeline path. [Incremental ThinLTO dependency reuse Rust#155](https://github.com/astral-sh/ohm-rust/pull/155) shows 14.82% uv binary-only edit benefit (later-three 12.00%), Ruff 2.97%(later-three 1.47%) mixed, and one uv library edit 83.592→89.664s regression. It requires ThinLTO profile selection; versus normal fat LTO uv executables grow 15.58% and resolution is 5.45–5.74% slower in that study. That tradeoff does not establish value for normal Ohm development or default production profiles. Keep as an isolated experiment only if a concrete user wants this niche.

[Coroutine subset guard Rust#141](https://github.com/astral-sh/ohm-rust/pull/141) demonstrates the appropriate simplification pattern: the larger +109/−29 prototype did not establish additional Codex benefit over +7/−0 guard. The reported selected-crate CPU gains are noisy/historical, and synchronous Ruff/ty cannot directly exercise the routine. A tiny defensible local guard is preferable to preserving the full prototype's machinery based on slightly larger uv point estimates.

## Evidence limits and smallest useful followups

Compiler CodSpeed's [current local methodology](../../external/ohm-rust/src/tools/codspeed/README.md) replays leaf compiler invocations with dependencies excluded, one frontend thread, full incremental hash verification, and a stage-1 compiler without release PGO/BOLT. The 22-case suite emphasizes four registry fixtures (five cases each) plus two real-crate checks. This is useful compiler engineering evidence, but small gains dominated by a fixture such as bitmaps are weak grounds for retaining semantic specialization in a parallel released development stack.

The current release comparison has good provenance and contamination controls: exact source/tools, balanced order, matching profiles/commands/test-start counts, pinned compatibility patches, no detected unrelated compilers,30-second preflight, and continuous host telemetry. Managed Falcon/service overhead remains in timings. These controls improve credibility; they do not create independent evidence for each optimization.

Coverage gaps that matter for simplification decisions:

- Only one 16-CPU EPYC host for current Linux timing; physical disk on one Apple M5/APFS system. No Windows benchmark, memory-pressure/concurrent-link benchmark, filesystem matrix, or broad single-thread versus parallel/frontend tradeoff.
- Released PGO/BOLT compiler differs from most component experiments' unprofiled stage1/2 compilers. Code-layout, allocator and optimizer interactions can erase or alter small historical gains.
- uv stock Full debug versus Ohm line tables is a real bundled default difference. All ablation cells use the same Ohm default, so that matrix is fair; stock-versus-Ohm uv totals do not isolate compiler reuse from debug policy.
- Current session runs opt into proc-macro trust=all; APFS study additionally native-tool trust=all. They measure a configured development workflow beyond packaged defaults. Strict-trust worktree value and cache failure/fallback frequency remain unmeasured.
- Published compiler accounting is Cargo status messages rather than actual rustc invocations. It cannot partition saving into early cutoff, query reuse, macro expansion, Cargo overhead or linking.
- Entire sessions have two repetitions per arm, cold/build-check/shared-worktree workflows one, APFS cohorts one. Most figures are preliminary point estimates without confidence intervals. Historical report numbers cannot isolate adjacent release changes.
- The historic corpus is three projects and a few edit histories; most deliberate dependency edits preserve API. Public-API changes, broad refactors, build-script/env changes, macros sensitive to external state, many tiny crates, and actual developer frequencies are not comprehensively represented.

Do not spend weeks proving every speculative patch useless. Remove clearly unneeded default-off experiments and complex sub-percent additions first, then benchmark the **simplified stack versus full stack** on a small, representative replay set. Preserve failing/slower cells and validate outputs/freshness against normal Rust.
