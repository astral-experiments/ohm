Ohm stack simplification review

Inventory frozen October 5, 2026; ablation findings updated October 7. Reviewed the seven astral-sh/ohm* repositories, the exact Ohm 1.99.0-1 release sources, and the material unshipped experiments. The inventory below uses that fixed release snapshot. Cargo #104/#115 have since been removed from the active stack; historical releases remain unchanged. Current ablation findings distinguish accepted measurements from held or unmeasured cases.

Keep the core that avoids dependency rebuilds, reuses executable objects and shares immutable worktree artifacts. Remove later formatter layers, restore upstream query promotion and retire the separate linker experiments. Cargo #104/#115 are already removed. A small positive result should earn its maintenance cost, especially when a change adds a cache protocol, semantic shortcut or metadata format.

Twenty-three representative-command comparisons have completed their raw-data audits. The results support removing rustfmt #18/#19 while accepting their measured costs, returning to serial query promotion and removing metadata-prefix reuse while accepting its first-edit costs. Removing the const-impl secondary index improves cold Ruff and uv checks, with both pairs agreeing; Codex edits have mixed costs. The line-table comparison supports keeping that deliberate development-profile choice. The Linux compiler allocator comparison supports returning to jemalloc with explicit Ruff costs and lower maximum-child memory. Removing the six-line Clippy MSRV shortcut also has measured costs, accepted for upstream parity. The individual CGU screens favor removing the 26-line caller-local policy with explicit Ruff and uv edit costs, while retaining the 34-line stable merging policy provisionally for Codex edits. The coroutine layout/debug screen supports removing #99/#132 together: 361 net production lines, accepting Codex no-op/Edit 1 costs of 144/433 ms while later edits improve. Formatter PGO has substantial first-format and edit benefits. Clippy PGO, its small clone and macro guards, and resolver caching remain provisional keeps; the smaller two-pair screens establish practical tradeoffs, without statistical significance claims. All fresh command results and limits.

The broader formatter and compiler-cache removals also have material costs. Package-only formatting removes 2,145 net lines but adds up to 910 ms to the measured dirty-file commands. Removing the compiler worker-cache/retention bundle costs Codex's cold check a paired median 5.97 s; all six pairs are slower. These results justify holding those broad removals while questioning their individual mechanisms. Proc-macro caching and dependency-read filters have mixed workload effects, including repeated losses on some Ruff or Codex edits. Formatter comparison, compiler-cache comparison, proc-macro comparison, read-filter comparison.

Clippy cache removal triggered a compiler panic on a real Codex edit; the saved trace and source review identify Rust #106's serialized-value forwarding as the strongest hypothesis, with individual causation still unproved. Sparse metadata and semantic shortcuts now have complete raw audits. Sparse removal raises maximum-child RSS by roughly 16–60 MiB in several states; that measured memory cost is accepted explicitly in the recommendation below. Current progress records the final disposition of every comparison, including held and unmeasured cases. The small-patch dispositions identify another 25 empty frozen commits that can leave the stack without changing source.

This report distinguishes removal recommendations, simplification/ablation candidates, features to retain provisionally, and experiments to hold or archive. These are maintenance judgments informed by the measurements; they are not claims that every proposed removal is behavior-neutral or loses zero performance. Fresh screens use the representative command matrix, reporting each cold/no-op/edit state without executing project tests. Native validation retains each variant’s recorded scope. The combined removal implementation has not been built or timed. Clippy retains the original --all-targets/--tests lint recipes; those targets are compiled and linted without executing the project test suite.

What the benchmark evidence does and does not establish

Fresh ablations time representative Cargo commands on pinned Ruff/ty, uv and Codex sources. Compiler checks and library builds each use five command states: cold, warm no-op and one command after each of three recorded edits. The edits are sequential; the compiler recipes do not include a revert. Codex Edit 1 adds transcript-layout bookkeeping, Edit 2 implements stable active-cell rendering with snapshots, and Edit 3 invalidates cached layouts when active cells are removed. Corrected BUILD labels and preserved originals document the presentation correction; measurements are unchanged. Clippy uses cold, no-op, direct-edit and dependency-edit commands; formatting records its relevant edit and fallback paths. These are selected targets, with zero timed project test executions. Library builds exercise code generation without final executable linking; uv's test-only third edit can be inactive for the selected library target.

Each arm starts with private target/shared histories. The earlier campaigns use six counterbalanced pairs per project; the later screens use two. Installation, optimized compiler builds, source preparation, native correctness and training are recorded separately from command timing. Whole pairs affected by unrelated activity are retained and excluded, then retried in their fixed slot with fresh histories. Removing a feature can be slower: the detailed tables preserve every command state, paired range and slower-pair count. Maximum-child RSS is a per-process measure, not total concurrent memory. Paired differences are calculated before taking the median; subtracting arm medians can give a different number. Two-pair screens show practical tradeoffs with limited precision.

The published release study improves the three measured sessions from 1,328.10 to 869.14 seconds, or 34.56%, with two repetitions per toolchain/project. That is material evidence for Ohm's overall value, but does not independently defend each included feature. APFS disk reductions are also substantial, with one/two/ten worktrees: roughly 40–50% for Ruff and 35–58% for uv. Those cohorts combine debug policy, shared storage, seeding and compiler format changes.

The most useful published factorial experiment toggles public API hashing and proc-macro expansion caching within the same release. API hashing saves 42.40% in that favorable parser-edit workflow. Proc-macro caching saves 2.72% averaged over the API settings; with API hashes on, the median difference is 0.123 seconds / 2.96%, but the two same-repetition differences have opposite signs and much larger variation. This is weak precision for a small gain. The expansion cache implementation is entirely upstream Rust 1.99; changing its automatic Cargo default does not delete compiler fork code. It also does not automatically justify deleting registry macro artifact reuse or local seed admission.

Two earlier eight-pair proc-macro campaigns were attempted on charlie-openai-2, with exact release binary/source hashes, independent warm histories and unchanged contamination guards. Both passed preflight and later encountered unrelated Cargo/rustc activity. Both campaign receipts failed acceptance. There is no accepted complete comparison from those attempts, and the partial cells are retained as exploratory evidence without a speedup claim. Generated targets and private worktrees were cleaned after source/ownership/process checks; original artifacts and toolchains were preserved. Details, hashes, receipts and raw packets are in the benchmark appendix; the current ordinary-command scope is recorded in ablation progress.

Several confounders materially affect retention decisions:

  • Debug policy: Ohm's line-table default differs from stock full development debug information. The published uv stock-versus-Ohm comparison includes this default difference; Ruff and Codex use matching explicit debug settings. Some impressive coroutine/span results use full debug and weaken under the current line-table default. Retain/revert profile choices deliberately and compare like profiles when pricing a compiler feature.

Recommendations

Remove the optional incremental configuration expiry feature

Cargo #104 is disabled by default. Its controlled experiment assigned three configurations artificial ages of 40 days, reclaimed 221.37 MiB of 349.42 MiB of logical incremental state, and preserved 97 finished artifacts. It does not demonstrate how often configurations really become stale, physical APFS savings, or a net benefit over ordinary cleaning. The next parser edit cost 0.903 seconds after expiry versus 0.244 seconds with the state retained.

The shipped implementation adds a 617-line module, new clean CLI behavior, changes to incremental directory selection and usage tracking, marker versions, ownership checks, hourly refresh logic, profile locking, and interrupted-deletion recovery. There are 777 lines of expiry integration tests and another 283 lines of reuse tests. The initial and hardening commits add +790/-119 in nonvendored source before later interactions. See incremental_gc.rs.

My judgment: remove this whole feature from the shipped Cargo stack. Preserve its report and experiment branch. Rust's separate superseded-session cleanup is a different feature and should not be removed with it. If expiry returns, require observed long-running disk pressure and a policy benchmark that includes the cost of rebuilding expired data.

Revert the dependency scheduler replacement

Cargo #115 replaces the upstream queue with dense indices, per-artifact counters, a binary heap, an iterative dependency walk and sparse transitive-reachability bitmaps. Its single file change is +322/-139; it adds a second representation of graph identity and changes equal-priority tie breaking.

The best recorded whole-Cargo instruction reductions are 0.27% for an unchanged Ruff check and 0.66% for an unchanged uv check. Neither invokes the compiler. Native elapsed no-op, edit and revert measurements are inconclusive and order-sensitive, and these Cargo binaries lacked release Cargo PGO. Compiler BOLT is irrelevant to these no-compiler commands. See dependency_queue.rs.

My judgment: the measured gain is too small for a wholesale replacement of upstream scheduling in this project. Revert to the upstream queue and preserve any tests that expose real upstream correctness gaps. No special benchmark is necessary to say the present evidence is insufficient; a future proposal should show a repeated representative session benefit, including concurrent builds.

Question the separate Cargo allocator fork

Cargo #106 has better independent evidence than the scheduler: matched PGO builds on an Apple M5 Max improve metadata and unchanged commands by 4.6–8.3%, including Ruff check 216→199 ms and uv build 296→267 ms. Linux did not establish a win and used more memory, so Cargo uses mimalloc only on Apple Silicon.

Its custom integration is small (+37/-1 outside vendored source), but it adds another copy of mimalloc 3.5.1, a CMake dependency and a bespoke native allocator build. That is 26,598 vendored lines, additional to the compiler's allocator source. The PR explains that the chosen Rust dependency bundled the older allocator, so blindly replacing this with that dependency would change the tested implementation.

My judgment: remove the Cargo-specific allocator integration. Its historical 17–29 ms warm-command savings are too small for the duplicate native vendor/build ownership under this simplification goal. The prepared removal passed independent source review: three integration files change by +1/-47, all 54 vendor files are deleted, the optional CMake dependency and orphan lock entry disappear, and the other optimizations retain their empty ohm-defaults feature gate.   • build_runner/mod.rs

Boundaries that should stay separate

Shared namespace construction is global and occurs before compiler execution. It includes Cargo/rustdoc/linker/native-tool identities, job count, configuration, bootstrap/version overrides and trust policies (compilation_files.rs:225–651). Cross-mode provenance additionally binds diagnostics and captures the actual child process after build-script overrides (build_runner/mod.rs:255–283, compiler/mod.rs:1363–1365). Reusing the initial global environment in place of that child capture loses a real correctness boundary. Cargo's synthesized dynamic-library search variable intentionally uses inherited values rather than an apparently forced [env] entry; preserve that rule in shared fact collection.

The dependency-graph eligibility check runs before CompilationFiles exists and can admit owned workspace libraries under workspace locking. The shared registry closure, by contrast, requires remote immutable packages and memoizes macro/native runtime policy along the actual unit closure. These final eligibility predicates should remain separate. One fact layer is enough; a polymorphic cache-admission framework or one universal eligibility boolean would make the contracts harder to review.

Narrow admission and flag surface

There are ten explicitly named ohm_* controls in features.rs:961–970, plus related embedding/relinking and locking controls. They are not ten independent binary switches: defaults derive several effective choices, linker/trust controls are enums, and shared caching requires fine-grained locking. Do not quantify the test burden as an unconstrained power-of-two count.

The most questionable extra admission tier is native build-scripts, between strict and all (features.rs:169–186). The documented user workflow chooses all; #82 explains narrower native tainting but provides no marginal timing or eligible-hit count for the intermediate tier. Ask the implementation to justify this tier with actual use and lost-hit coverage. Removing it alone saves only a few match/parser/test branches, not the authentication or native closure implementation. It is a modest surface cleanup, not a large code-removal claim. Retain a conservative default and an explicit permissive opt-in if broad native reuse remains an intended workflow.

The two trust domains should not be collapsed into one trust-all control: macro trust also authorizes local workspace snapshot imports, whereas native trust controls authenticated registry artifacts. Their risks and lifetimes differ. Likewise, the audited_macro_runtime and permissive_native_runtime recursion states in compilation_files.rs:1571–1634 are needed by the retained policies, rather than arbitrary generic modes that can simply disappear.

The independent Clippy seed override deserves a smaller follow-up: shipped automatic selection already derives from worktree seeding, bundled Clippy and file-clone support (compilation_files.rs:609–642). Some(true) bypasses the automatic clone capability selection. The override also supports useful ablation/debugging, so its existence alone is not evidence to remove isolation. Other strong flag removals follow feature deletion, especially incremental expiry and the focused-test prototype; retaining dead switches after deleting those features would preserve unnecessary states.

Restricting optimized admission to shipped native targets could reduce cross-target policy obligations while preserving ordinary Cargo fallback, but native targets can still be replaced through RUST_TARGET_PATH, local target JSON and custom compiler backends. Narrowing eligibility does not make those checks dispensable. Measure current cross-target hit coverage before deciding whether the reduced cache coverage is acceptable; this source audit supplies no evidence that cross-compilation reuse is unused.

Actual eligibility is much narrower than "coalesces shared-cache misses": fine-grained locking, an authenticated shared unit, Build/Check mode, a library that is not a procedural macro, and zero unit dependencies (fingerprint/mod.rs:970–984). Wild compact artifacts: distinct unshipped feature

PR #32 reads RCOBJ001 compact objects directly, including members of conventional .rlib archives. It adds1,304 lines in compact-artifact/src/lib.rs,414 in library.rs,79 CLI lines,43 .dwo helper lines and Wild file-kind/input/section integration. A compact object is not ELF: its eager metadata uses tagged section offsets and independently compressed cold payload blocks. The same crate must coordinate with rustc emission/export/fallback and Cargo lifecycle logic.

This is a storage architecture change, not another2% linker optimization. Evaluate it against physical disk saving and complete clean/build/edit/test/Clippy/export/debugger lifecycles, not merely standalone link time. Ohm #140 measurements used Wild dba82ebe; current Wild head 9179eb98 has later validation/CI changes and the raw metadata allocation-bound repair. The current PR says24 CI checks pass, but binary identity with the measured artifact has not been checked.

Two separately removable layers deserve skepticism:

  • WILD_COMPACT_CACHE_BYTES adds file-backed streaming decode, a global logical LRU working set, weak references, eviction/advice bookkeeping and unsafe page-discard advice. Borrowed slices keep their mappings; actual RSS, eager metadata, active reads and OS page cache are not capped. Backing files can approach the full decoded selected payload. This is an opt-in memory/I/O experiment, not needed by default pinned in-memory decode. Retain only with independent pressure measurements proving useful net behavior.
  • RCLIB001 external store manifests keep backward-readable versions1/2, relocation/ancestor-store lookup, separate metadata and content-addressed members, plus wild-pack archive/references/inspect/export tooling. Conventional archives containing compact objects provide a potentially simpler format boundary. Removing manifests is feasible only after confirming rustc/Cargo/clean/export no longer consume that representation; the compiler agent owns that dependency decision.

Do not delete decoder validation, section-size checks, metadata bounds or the debug-compression padding/TLS repairs in the name of simplification while retaining compact inputs. These are correctness requirements for the selected format. If abandoning compact formats entirely, delete compiler emit/export, Cargo detection/lifecycle and Wild reader support together, then use released upstream Wild.

Evidence limits and smallest useful followups

Compiler CodSpeed's current local methodology replays leaf compiler invocations with dependencies excluded, one frontend thread, full incremental hash verification, and a stage-1 compiler without release PGO/BOLT. The 22-case suite emphasizes four registry fixtures (five cases each) plus two real-crate checks. This is useful compiler engineering evidence, but small gains dominated by a fixture such as bitmaps are weak grounds for retaining semantic specialization in a parallel released development stack.

The published release comparison has good provenance and contamination controls: exact source/tools, balanced order, matching profiles/commands/test-start counts, pinned compatibility patches, no detected unrelated compilers,30-second preflight, and continuous host telemetry. Managed Falcon/service overhead remains in timings. These controls improve credibility; they do not create independent evidence for each optimization.

Coverage gaps that matter for simplification decisions:

  • The published release study uses one 16-CPU EPYC host for Linux timing; physical disk is measured on one Apple M5/APFS system. No Windows benchmark, memory-pressure/concurrent-link benchmark, filesystem matrix, or broad single-thread versus parallel/frontend tradeoff.
  • Released PGO/BOLT compiler differs from most component experiments' unprofiled stage1/2 compilers. Code-layout, allocator and optimizer interactions can erase or alter small historical gains.
  • uv stock Full debug versus Ohm line tables is a real bundled default difference. All ablation cells use the same Ohm default, so that matrix is fair; stock-versus-Ohm uv totals do not isolate compiler reuse from debug policy.
  • Published session runs opt into proc-macro trust=all; APFS study additionally native-tool trust=all. They measure a configured development workflow beyond packaged defaults. Strict-trust worktree value and cache failure/fallback frequency remain unmeasured.
  • Published compiler accounting is Cargo status messages rather than actual rustc invocations. It cannot partition saving into early cutoff, query reuse, macro expansion, Cargo overhead or linking.
  • The published entire sessions have two repetitions per arm, cold/build-check/shared-worktree workflows one, APFS cohorts one. Most figures are preliminary point estimates without confidence intervals. Historical report numbers cannot isolate adjacent release changes.
  • The historic corpus is three projects and a few edit histories; most deliberate dependency edits preserve API. Public-API changes, broad refactors, build-script/env changes, macros sensitive to external state, many tiny crates, and actual developer frequencies are not comprehensively represented.
